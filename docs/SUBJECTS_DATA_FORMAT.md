# Формат предметов и замена банка вопросов

## 1. Где лежат предметы

Самодостаточные банки и манифесты предметов находятся здесь:

```text
data/
└── subjects/
    ├── pharmacology.json
    ├── anatomy.json
    ├── biology.json
    └── _subject_template.json
```

**Один самодостаточный JSON или один JSON-манифест = один предмет.**

Файлы, начинающиеся с `_`, сборщик игнорирует. Поэтому `_subject_template.json` можно хранить рядом как шаблон.

Чтобы добавить новый предмет:

1. Создать готовый рабочий банк одной командой:

```bash
python tools/new_subject.py --id anatomy --title "Анатомия" --order 30
```

Команда создаёт `data/subjects/anatomy.json` с одним рабочим примером каждого типа
вопроса. Файл сразу проходит проверку, поэтому ошибиться в структуре JSON на старте
невозможно. Дальше достаточно отредактировать тексты и варианты ответа.

2. Наполнить банк своими вопросами.

3. Проверить и пересобрать данные из корня проекта:

```bash
python tools/build_data_bundles.py --check    # только проверка, ничего не пишет
python tools/build_data_bundles.py            # генерация runtime-файлов
python tools/verify_runtime_bundle.py         # проверка собранного бандла
```

4. После успешной генерации пересобрать APK в Android Studio.

Вместо команды можно скопировать `_subject_template.json`, переименовать копию в
`anatomy.json` и заполнить `subject` и `questions` вручную. Полный пример каждого
типа лежит в `templates/subject_bank_template.json`, пример банка только из билетов —
в `templates/tickets_subject_template.json`.

Вручную редактировать файлы в `app/src/main/assets/subject_data/` и `subjects_core.js` не нужно: это сгенерированные runtime-файлы.

## 2. Метаданные предмета

Минимальный файл предмета:

```json
{
  "schema_version": "2.2-subject-bank",
  "subject": {
    "id": "anatomy",
    "title": "Анатомия",
    "language": "ru",
    "order": 20
  },
  "questions": []
}
```

### `subject.id`

Технический постоянный идентификатор предмета.

Разрешены:

- латинские строчные буквы;
- цифры;
- `_`;
- `-`.

Примеры:

```text
pharmacology
anatomy
biology
pathological_anatomy
microbiology-1
```

**Не меняйте `id` после выпуска приложения**, если хотите сохранить пользовательский прогресс этого предмета. Прогресс хранится отдельно по `subject.id`.

### `subject.title`

Название, которое пользователь видит в приложении:

```json
"title": "Анатомия"
```

Именно оно показывается в верхней части приложения и в меню выбора предмета.

### `subject.order`

Необязательное целое число. Чем меньше число, тем выше предмет в списке.

Например:

```json
"order": 10
```

Если `order` не указан, используется `1000`, после чего предметы сортируются по названию.

### `question_count`

В исходном JSON **не нужен**. Сборщик самостоятельно считает общее число заданий, число билетов и число автоматически проверяемых вопросов.

## 3. Типы вопросов

Канонические типы, которые понимает приложение:

```text
single_choice    один правильный вариант
multiple_choice  несколько правильных вариантов
open_text        текстовый ответ
matching         соответствие
ticket           билет с развёрнутым ответом
```

При записи банка доступны сокращения, которые сборщик сам разворачивает в
канонические типы:

```text
true_false  / boolean   -> single_choice с двумя вариантами «Верно / Неверно»
sequence    / ordering  -> matching, где каждая позиция используется один раз
card        / flashcard -> ticket
```

ID заданий должны быть уникальны **внутри одного предмета**. У разных предметов одинаковые ID допустимы.

### 3.1 Сокращения

`true_false` — утверждение и правильность:

```json
{
  "id": 10,
  "type": "true_false",
  "question": "Верно или неверно: кровь переносит кислород только эритроцитами",
  "answer": false,
  "explanation": { "answers_markdown": "Кислород переносит и плазма." }
}
```

`answer` принимает `true` / `false`, а также строки `да`, `нет`, `верно`,
`неверно`, `1`, `0`. Подписи вариантов меняются через `true_label` и
`false_label`.

`sequence` — этапы в правильном порядке:

```json
{
  "id": 11,
  "type": "sequence",
  "question": "Расположите стадии митоза",
  "steps": ["Профаза", "Метафаза", "Анафаза", "Телофаза"],
  "correct_order": [1, 2, 3, 4]
}
```

`correct_order` содержит номера `1..N`: `steps[i]` стоит на позиции
`correct_order[i]`. Порядок `1,2,3,4` означает, что этапы уже перечислены
правильно; для перемешанного списка укажите, например, `[3, 1, 4, 2]`.

`card` — карточка для запоминания:

```json
{
  "id": 12,
  "type": "card",
  "front": "Апоптоз",
  "back": "**Программная гибель клетки.** Активируется каспазами."
}
```

### 3.2 Сокращения при записи вариантов ответа

`id` вопроса можно не указывать: сборщик проставит последовательные значения.
Варианты ответа можно записать обычным списком строк, а правильный указать
номером или номерами:

```json
{
  "id": 13,
  "type": "single_choice",
  "question": "Какой орган синтезирует инсулин?",
  "options": ["Печень", "Поджелудочная железа", "Селезёнка"],
  "correct": 2
}
```

Для `multiple_choice` `correct` может быть списком: `"correct": [1, 3]`.

## 4. Один правильный ответ

```json
{
  "id": 1,
  "type": "single_choice",
  "question": "Текст вопроса",
  "options": [
    {
      "id": 1,
      "text": "Вариант 1",
      "correct": false
    },
    {
      "id": 2,
      "text": "Вариант 2",
      "correct": true
    }
  ],
  "explanation": {
    "topic_markdown": "Разбор темы",
    "answers_markdown": "Разбор вариантов",
    "correct_answer_markdown": "**2. Вариант 2**"
  }
}
```

Для `single_choice` должен быть ровно один правильный вариант.

`correct_option_ids` писать необязательно: сборщик сам создаёт его из `correct: true`.

---

## 5. Несколько правильных ответов

```json
{
  "id": 2,
  "type": "multiple_choice",
  "question": "Выберите правильные варианты",
  "options": [
    {
      "id": 1,
      "text": "Вариант 1",
      "correct": true
    },
    {
      "id": 2,
      "text": "Вариант 2",
      "correct": false
    },
    {
      "id": 3,
      "text": "Вариант 3",
      "correct": true
    }
  ],
  "explanation": {
    "topic_markdown": "Разбор темы",
    "answers_markdown": "Разбор вариантов",
    "correct_answer_markdown": "**1. Вариант 1**\n\n**3. Вариант 3**"
  }
}
```

## 6. Текстовый ответ

```json
{
  "id": 3,
  "type": "open_text",
  "question": "Введите термин",
  "accepted_answers": [
    "Основной вариант",
    "Допустимый вариант"
  ],
  "explanation": {
    "topic_markdown": "Разбор темы",
    "answers_markdown": "Почему этот термин является ответом",
    "correct_answer_markdown": "**Основной вариант**"
  }
}
```

Любая строка из `accepted_answers` считается правильной.

По умолчанию при проверке игнорируются регистр, повторные пробелы и различие `е/ё`.
Если регистр действительно важен, включите `case_sensitive`:

```json
{
  "id": 30,
  "type": "open_text",
  "question": "Введите ФИО латиницей",
  "accepted_answers": ["Hippocrates"],
  "case_sensitive": true
}
```

Тогда `hippocrates` будет признан неправильным. В `accepted_answers` нельзя
оставлять два ответа, отличающихся только регистром: сборщик сочтёт их лишними и
остановит сборку с понятным сообщением.

## 7. Соответствие

```json
{
  "id": 4,
  "type": "matching",
  "question": "Установите соответствие",
  "left_items": [
    {
      "id": 1,
      "text": "Левая позиция 1"
    },
    {
      "id": 2,
      "text": "Левая позиция 2"
    }
  ],
  "right_items": [
    {
      "id": 1,
      "text": "Правая позиция 1"
    },
    {
      "id": 2,
      "text": "Правая позиция 2"
    }
  ],
  "correct_mapping": [
    {
      "left_id": 1,
      "right_id": 2
    },
    {
      "left_id": 2,
      "right_id": 1
    }
  ],
  "explanation": {
    "topic_markdown": "Разбор темы",
    "answers_markdown": "Разбор соответствий",
    "correct_answer_markdown": "1 → 2; 2 → 1"
  }
}
```

Каждая левая позиция должна иметь ровно одно правильное соответствие. Один и тот же правый вариант **может использоваться несколько раз**.

## 8. Билет с развёрнутым ответом

Билет не содержит вариантов ответа и не проверяется автоматически. Пользователь видит формулировку, нажимает **«Показать ответ»**, читает развёрнутый ответ и вручную выбирает **«Знаю»** или **«Повторить»**.

Минимальный формат:

```json
{
  "id": 5,
  "type": "ticket",
  "ticket": "Фармакокинетика: всасывание, распределение, метаболизм и выведение лекарственных средств",
  "answer_markdown": "**Фармакокинетика** изучает...\n\nДалее полный развёрнутый ответ на билет."
}
```

Допустимо вместо `ticket` использовать поле `question`, но для билетов рекомендуется именно `ticket`, чтобы исходные данные было проще читать.

Для ответа можно использовать:

- `answer_markdown` — предпочтительный вариант, поддерживает `**жирный текст**` и абзацы;
- `answer_text` — обычный текст без Markdown.

Хотя бы одно из этих двух полей обязательно.

При необходимости к билету можно дополнительно добавить обычный блок `explanation`, но основной текст билета должен лежать в `answer_markdown` / `answer_text`.

### Как билеты участвуют в режимах

- **Учить → По порядку** — билеты идут вместе с остальными заданиями по ID.
- **Учить → Случайно** — билеты могут выпадать как обычные задания.
- **Только ошибки** — билет попадает сюда, если после просмотра ответа нажать «Повторить».
- **Банк** — билет отображается как тип `Билет` и открывается для просмотра.
- **Тест** — билеты автоматически исключаются, потому что у них нет машинно проверяемого ответа. Если предмет содержит только билеты, вкладка «Тест» сообщает, что тестовых вопросов нет.

Прогресс билета хранится так же, как у остальных заданий: «Знаю» закрывает билет, «Повторить» добавляет его в очередь повторения.

---

## 9. Разборы необязательны

Поле `explanation` можно полностью не указывать. Вопрос всё равно будет работать в обучении и тесте.

Если разбор есть, приложение поддерживает:

```json
"explanation": {
  "topic_markdown": "...",
  "answers_markdown": "...",
  "correct_answer_markdown": "..."
}
```

Первые два поля выводятся как сворачиваемые блоки.

## 10. Что создаёт сборщик

Из всех файлов `data/subjects/*.json` автоматически создаются:

```text
app/src/main/assets/
├── subjects_core.js
└── subject_data/
    ├── biology_ex_000.js
    ├── biology_ex_001.js
    ├── ...
    └── pharmacology_ex_000.js
```

`subjects_core.js` содержит:

- список предметов;
- название каждого предмета;
- общее число заданий;
- число билетов и число тестовых вопросов;
- структуры вопросов и билетов;
- ключи правильных ответов для автоматически проверяемых типов.

Длинные разборы и развёрнутые ответы на билеты выносятся в отдельные небольшие
файлы. В `subjects_core.js` попадает только индекс предмета
`explanations_index`: какой вопрос в каком файле. Приложение подгружает нужный
файл целиком, когда разбор впервые понадобился, и больше его не читает. Поэтому
банк на тысячи вопросов не замедляет запуск приложения.

Файлы разборов полностью генерируются: при сборке устаревшие файлы удаляются, так
что в APK не попадает мёртвый код.

## 11. Добавление предмета в Android Studio — коротко

Например, нужно добавить анатомию.

Создайте рабочий банк одной командой:

```bash
python tools/new_subject.py --id anatomy --title "Анатомия" --order 20
```

В начале полученного файла:

```json
{
  "schema_version": "2.2-subject-bank",
  "subject": {
    "id": "anatomy",
    "title": "Анатомия",
    "language": "ru",
    "order": 20
  },
  "questions": [
    ...
  ]
}
```

Затем из корня проекта:

```bash
python tools/build_data_bundles.py --check
python tools/build_data_bundles.py
```

После сообщения вида:

```text
Собрано предметов: 3
  anatomy: Анатомия — 500 заданий (40 билетов, 460 проверяемых), разборов 500 в 9 частях
```

можно собирать APK:

```bash
./gradlew assembleDebug
```

или через Android Studio: **Build → Build APK(s)**.

Никаких изменений в `app.js`, `MainActivity.java` или `AndroidManifest.xml` для нового предмета не требуется.

## 12. Отдельные файлы билетов и тестов

Сборщик версии 1.3.0 поддерживает манифест с массивом `imports`. Это позволяет оставить билеты и тесты в отдельных файлах и объединить их только во время генерации runtime-данных.

Минимальный манифест:

```json
{
  "schema_version": "2.2-subject-import",
  "subject": {
    "id": "biology",
    "title": "Биология",
    "language": "ru",
    "order": 20
  },
  "imports": [
    {
      "path": "../imports/biology/tickets.json",
      "format": "exam_tickets_v1",
      "id_offset": 0
    },
    {
      "path": "../imports/biology/tests.json",
      "format": "exam_tests_v1",
      "id_offset": 10000
    }
  ]
}
```

Поддерживаются `auto`, `canonical`, `exam_tickets_v1` и `exam_tests_v1`. Значение `id_offset` прибавляется к каждому исходному ID подключаемого файла. Оно должно устранять пересечения и оставаться неизменным после выпуска.

Формат подключаемого файла определяется автоматически, если `format` не указан.

## 13. Прогресс пользователей и изменение банка

Прогресс хранится по паре «`subject.id` + `id` вопроса». Отсюда два правила:

| Действие | Что будет с прогрессом |
| --- | --- |
| Удалить вопрос из банка | Запись о нём молча отбрасывается, остальное сохраняется |
| Добавить новые вопросы | Ничего не теряется |
| Изменить `id` существующего вопроса | История этого вопроса теряется |
| Переименовать `subject.id` | Теряется весь прогресс предмета |
| Переставить вопросы в файле | Ничего не теряется, если `id` остались прежними |

Приложение не падает на старте, если в сохранённом прогрессе остались ID
несуществующих вопросов: такие записи выбрасываются при загрузке. Это позволяет
уменьшать банк и обновлять приложение без миграции данных.

Ещё одно поле на заметку: `subject.title` можно менять свободно — пользователь
видит только его.

Поля `ticket_number`, `ticket_question_number`, `topic`, `subtopic`, `difficulty` и `skill` необязательны. Если они есть, приложение использует их для подписей, расширенного поиска и фильтра теста по билету.

Подробности: `docs/IMPORTING_PAIRED_BANKS.md`.
